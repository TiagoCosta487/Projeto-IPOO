# Projeto-IPOO
*Desenvolvimento do projeto final de IPOO*

## Plano de trabalho sugerido
Esta seria a sequência que seguiria desde agora até à apresentação:

**1. Preparação independente do tema**
   Podes fazer agora
   
   - Criar repositório GitHub.
   - Criar estrutura de pastas.
   - Preparar modelos de documentação.
   - Criar quadro de tarefas.
   - Definir convenções de diagramas.
     
**2. Definição do projeto**
   Após escolher o tema

   - Identificar problema e objetivos.
   - Definir âmbito e limitações.
   - Identificar atores.
   - Definir requisitos funcionais e não funcionais.
   - Elaborar documento de requisitos.
     
**3. Modelação do sistema**

   - Elaborar casos de uso.
   - Identificar entidades.
   - Definir relações entre classes.
   - Construir diagrama de classes.
   - Verificar se existem pelo menos 20 classes contextualizadas.
     
**4. Desenvolvimento Kotlin**

   - Criar estrutura do projeto.
   - Implementar classes.
   - Implementar relações e comportamentos.
   - Desenvolver interface de interação.
   - Implementar leitura/escrita de ficheiros ou acesso à internet.
     
**5. Testes e conclusão**

   - Testar operações CRUD.
   - Verificar comunicação entre classes.
   - Testar persistência dos dados.
   - Corrigir erros.
   - Preparar apresentação e demonstração.

Vamos por partes.
A. Criar um modelo de documentação de requisitos
Esta é provavelmente a parte mais importante, dado que a entrega parcial consiste precisamente no documento de requisitos.

Podes criar um documento com esta estrutura:

1. Introdução
- Contextualização do problema.
- Objetivo geral do sistema.
- Objetivos específicos.
- Âmbito do projeto.
2. Descrição do sistema
- Descrição geral.
- Público-alvo.
- Tipos de utilizadores.
- Funcionalidades principais.
- Limitações do sistema.
3. Requisitos funcionais
- RF01 – ...
- RF02 – ...
- RF03 – ...
4. Requisitos não funcionais
- RNF01 – Segurança.
- RNF02 – Usabilidade.
- RNF03 – Fiabilidade.
- RNF04 – Persistência de dados.
5. Casos de uso
- Identificação dos atores.
- Descrição dos casos de uso.
- Diagramas UML.
6. Modelação
- Identificação das entidades.
- Relações entre entidades.
- Diagrama de classes preliminar.
Naturalmente, os requisitos concretos só serão preenchidos depois de escolheres o tema.
B. Preparar modelos de casos de uso
Podes criar um ficheiro Draw.io com uma estrutura vazia para os futuros casos de uso.

Por exemplo, independentemente do tema, é bastante provável que existam atores como:
- Utilizador comum.
- Administrador.
- Funcionário/operador (dependendo do sistema).
E operações transversais como:
- Iniciar sessão.
- Consultar informação.
- Criar registos.
- Atualizar registos.
- Remover registos.
- Terminar sessão.
Não significa que todos estes casos de uso tenham de existir no teu projeto. São apenas pontos de partida.
C. Preparar um modelo de diagrama de classes
Ainda não podes definir as classes concretas, mas podes preparar o estilo e as convenções que vais utilizar.

Recomendo que estabeleças desde já:
- Atributos privados (-).
- Métodos públicos (+).
- Tipos de dados explícitos.
- Identificação de classes abstratas.
- Identificação de interfaces.
- Cardinalidades nas associações.
- Herança, composição e agregação quando aplicáveis.
Podes também definir uma legenda de cores para distinguir categorias de classes, facilitando a leitura do diagrama.
D. Preparar a gestão do projeto
No GitHub, podes utilizar o separador Projects para criar um quadro de tarefas.



Isto também te ajuda a demonstrar organização e evolução do trabalho através dos commits.
